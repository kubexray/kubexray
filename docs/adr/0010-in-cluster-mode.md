# 0010. In-cluster mode: always-on recording

- Status: Accepted
- Date: 2026-10-24

## Context

The local binary (ADR-0007) records only while someone has it open. The incident from 3 a.m. is gone by morning. v0.4's promise is a recorder that runs in the cluster around the clock, survives restarts, and can be installed with `helm install` ([roadmap](../../ROADMAP.md)).

Running inside the cluster changes the threat model:

- **The UI is reachable over the network**, not only from 127.0.0.1. Anyone who can reach the Service could otherwise see the cluster's structure, image names and who changed what.
- **The process holds a ServiceAccount** with cluster-wide read access, which an attacker would want.
- **History is kept for days**, so it has to live on disk with bounded size.

## Decision

### 1. One binary, a new command

`kubexray serve` runs the recorder, the cause engine and the web UI without a browser or terminal. It uses the in-cluster ServiceAccount (or a kubeconfig outside the cluster) and listens on `--listen` (default `:8080`). Everything the local UI does, it does: live map, rewind, incidents, `why`, export, diff.

### 2. Authentication is always on

There is no anonymous mode. Two modes:

| Mode | How it works | When |
|---|---|---|
| `token` (default) | A random token from a Kubernetes Secret (generated by the chart, or the user's own). Browsers open `/?token=…` once and get an HttpOnly, SameSite=Strict session cookie, as in ADR-0007; API clients send `Authorization: Bearer`. The token is compared in constant time | `kubectl port-forward`, or an Ingress the user secures with TLS |
| `proxy` | kubexray listens on **127.0.0.1 only**, inside the pod, and an auth proxy sidecar (oauth2-proxy or similar, supplied by the user) is the only way in | Single sign-on |

`--auth=none` is accepted only with a loopback `--listen` address; the binary refuses to start otherwise. `/healthz` answers without authentication and returns no data.

The cookie is marked `Secure` when `--secure-cookie` is set (TLS at an Ingress). The Host check of ADR-0007 becomes an allow-list: `localhost`/`127.0.0.1` (port-forward) plus `--allowed-host` names. The WebSocket Origin must match the request's host over http or https.

### 3. Least privilege, and Secrets are opt-in

The chart's ClusterRole has only `get`, `list` and `watch` on the kinds kubexray maps. kubexray watches Secrets as metadata only (ADR-0003), but RBAC can't express "metadata only": `list secrets` grants their contents. So **Secret access is off by default** (`rbac.secrets: false`). Without it, kubexray skips the Secret informer, and the cause engine never reports a Secret as missing, since it can't know. Turning it on brings back Secret edits as causes; the values file says what it grants.

The pod runs as non-root with a read-only root filesystem, no capabilities, `seccompProfile: RuntimeDefault`, and no ServiceAccount token beyond its own.

### 4. Recording on disk

With `--data-dir`, each completed segment (a keyframe and its deltas, ADR-0003) is written as one gzip NDJSON file, atomically (write to a temporary file, then rename). Only the segment being recorded is in memory, so a crash loses at most one segment (30 s by default). An index of segment times is kept in memory; segments are read from disk when rewinding or exporting, with a small cache.

Retention is by age (`--retention`, default 7 days) and by total size (`--retention-size`, default 1 GiB), whichever comes first; the oldest segments go first.

### 5. Restarts

A restarted process starts a new sequence (ADR-0003). Recorded history from before the restart stays available for rewinding: each segment stands alone (it starts with a keyframe). Exports (ADR-0008) must be one continuous sequence, so a window that spans a restart starts at the first segment after the restart; the response says so.

### 6. Packaging

A Helm chart in `charts/kubexray`:
- a Deployment with one replica and the `Recreate` strategy, because the volume is ReadWriteOnce
- a ServiceAccount, ClusterRole and binding
- a ClusterIP Service
- a PersistentVolumeClaim
- the token Secret, kept across upgrades
- optionally an Ingress and a NetworkPolicy

It is tested in CI by installing it on kind and checking authentication and persistence across a pod restart.

## Consequences

- History survives the night and pod restarts; sharing a replay link works from a recording made while nobody was watching.
- Exposing kubexray is an explicit act (an Ingress, a proxy), and even then nothing is anonymous.
- Without Secret access, a Pod that references a missing Secret gets a diagnosis from the kubelet's message (ADR-0009) but not a "missing Secret" cause. That's the trade for not holding read access to every Secret in the cluster.
- The disk format is the replay format's message lines, so recorded segments can later be exported or inspected with standard tools.
